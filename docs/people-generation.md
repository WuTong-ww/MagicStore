# 原创新来客与专属案例

主游戏现在可以通过首页配置的 Chat Completions 接口，在后台创作新的顾客及独立关联人。生成结果先做结构检查，再由另一轮模型请求审核；审核绑定同一草稿的 SHA256。本地重新核对姓名、编号、关系、配额和来源，成功保存后才安排到店。大模型不能直接写存档、改金币或替换已经存在的人物。

## 玩家流程

1. 在首页「设置」填写 URL、模型和 API Key，正常经营即可。后台并发与配额由配置文件控制，游戏不显示这些技术参数或审核流程。
2. 审核入档的新顾客会按营业时间分散到店，在前台或「候客与档案」正常接待。候客期间仍有耐心、个人时间窗和离店规则。
3. 新人物有自己的背景、偏好、口吻、来意、提问、逐步披露的细节与可核对材料，不套用固定人物的旧物案。明确询问关系后，可经来客同意请其介绍关联人；关联人使用自己的身份与视角，不继承主角的秘密。
4. 交谈后可以「约好下次」，双方确认时间后与结束接待一并保存。次日或合适的个人空档再次来访，保持同一个人物 ID，使用新的接待 ID；此前实际说过的话、服务记录和已披露线索继续保留。
5. 「候客与档案」中的已结识来客列表可以查看背景、偏好、已知关系和共同记忆。未认识人物的完整档案和隐藏案情不会进入这里。

固定剧情人物和原有本地来客规则仍可运行。缺少接口、服务失败或新设定未通过审核时，现有来客照常接待；被拒绝的草稿不会冒充成功生成的人物。

## 后台配置

`data/people/generation.json` 管理后台创作：

|参数|默认值|含义|
|---|---:|---|
|`concurrency`|2|同时在途的后台模型请求上限；生成与审核共用这个上限|
|`ready_target`|6|预备尚未见面的已审核新来客目标数量|
|`new_people_per_day`|8|每个游戏日新入档的主来客上限；关联人随同建档，不自动同时到店|
|`max_attempts_per_day`|16|每个存档、每个游戏日、当前进程中的生成任务尝试预算，防止失败后无限重试|
|`min_lead_minutes`|30|保留旧配置兼容；G1只填尚未到店的既定名额，不重新推迟到店|
|`arrival_spacing_minutes`|30|保留旧配置兼容；G1起到店时刻由既定日计划决定|
|`role_hints`|8 类日常职业|提供不同创作方向；姓名、经历、口吻和具体困扰仍由模型创作|

目标数量不是服务成功率或时间保证。结构检查、审核、限流和服务故障都可能使实际准备数量暂时少于目标。创建失败会退避重试；已经审核通过的其他人物仍可独立入档，不会被同批失败任务拖住。

`data/people/templates.json` 的 `arrival` 管理统一客流：自然客量按基础值、口碑、经验、限时加成、星期和天气之和为期望值进行泊松抽样，允许零客日，仅第0天保留固定新手客。到店时刻为午间/傍晚双峰加底噪；集中到店事件另有3–5人在30分钟内来访。在线生成人物只填已有未来自然客或集中来客名额，原到店时间、来源及日计划不变，不再额外补客。所有自然来客、预约、介绍与回访共用每日 **20** 个名额，室内候客容量为 **6**。改期保留原日期的占额记录，不能反复改期绕过上限；某日已满时按个人时间窗寻找后续可用日期。满员时按性格与紧急度选择门外等、预约请求或离开；门外补位不刷新耐心，请求须经同意才预约。临时空店时可在前台点「等一会儿」，最多推进30游戏分钟，不越过打烊。旧档已规划日不重算；分布目标、流失与迁移验收见[当前功能与验收](features.md#G1-每日客流2026-11-20)。

后台参数只由开发配置和测试接口使用，不在玩家设置、候客面板或对白中展示。API Key 仅在当前进程内存中使用。切换存档、配置或关闭服务会取消旧任务并清理凭据与计时器，迟到的回复不能落入新档。

## 初始创作与既有事实

创建时模型可以提出尚不存在的人物事实；审核入档后，这些初始设定被冻结。程序分配人物、关系、诉求、案例和线索的稳定编号，生日、基础耐心、外观部件与个人时间窗也有一致性校验。熟悉度、信任和候客后的回访倾向按合法事件变化，不能把这些变化误判成身份篡改。

生成包的结构为：

```text
version
person: name / role / personality / speech_style / background / preferences
contact: 同样六项人物资料
relationship: kind / shared_history
case: title / opening / question / situation / concern / detail / hidden_fact / followup
```

`situation` 和 `concern` 是初始公开诉求，`detail` 需要明确询问，`hidden_fact` 需要先了解细节再询问核对依据。隐藏材料必须是来客本人已经知道、实际持有并能出示的材料，不能突然读出另一人的内心，也不能预先确定未来结局。

对话阶段只发送当前人物的公开设定、真实来访和共同记忆，以及本次所选的获准资料。其他人物的案情、未选择话题的答案和本地保护规则不会进入对白生成器。玩家指认的新身份、传闻和预测保留为相应类型的数据，不能改成世界事实。

`relationship.shared_history` 属于两位 NPC 之间的内部往事，保留作初始事实的一致性记录，不自动成为玩家的共同记忆。关系话题只公开姓名与关系类型；玩家可见线索、事实和术式解读使用同一公开投影。关联人的案例也不引用主来客的内部往事或私密材料。

独立对白审核和本地保护同时运行。引用了某话题却没有真正说出其材料不能据此发线索；只引用人格或旧记忆的回复保持零新线索效果。回访会继承同人物、同案例的真实已知线索；尚未完整披露私密材料时使用中性开场，防止创建包中的回访计划暗示秘密。

## 实现位置

- `scripts/people/generated_person.gd`：生成/审核提示、严格结构、哈希、身份与来源冻结、双人物关系、原子入档候选。
- `scripts/providers/http_person_provider.gd`：独立后台并发池、生成与审核、取消、迟到回包、限流退避、前台对白优先；不修改游戏状态。
- `scripts/core/game_state.gd`：后台补充与完成队列，在前台空闲时重新校验最新状态并保存；每日预算与跨档隔离。
- `scripts/divination/generated_cases.gd`：从已批准生成包构建当前存档独立目录；`session.gd`、`case_save.gd` 负责服务、已知线索继承和恢复验证。
- `scripts/shop/people_bridge.gd`：正式来访、关系披露、介绍、预约与公共时钟/存档整合。
- `server/ai/person_generation.py`、`server/ai/gateway.py`：网关模式同构审核，独立后台容量，动态话题先分类后仅投影所选资料。Godot 与 Python 使用永久中文样例检查规范 JSON 和哈希一致。

新案例支持已适配的塔罗、雷诺曼、梅花、易经和小六壬。出生时刻、前世证据和邀请案未来事件不由创作模型随意补齐；这些专用机制继续使用原有案例契约。当前实现提供有界原创人物与案例，不宣称可任意生成整个世界或可靠模拟无限自主生活。

## 测试与真实接口验证

日常回归使用隔离 `.tools` 目录和本机假服务，不调用上游：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dev/run.ps1 -Test
```

真实测试单独运行，在当前终端进程提供 `MAGIC_LIVE_API_URL`、`MAGIC_LIVE_MODEL`、`MAGIC_LIVE_API_KEY`：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dev/run-live-people.ps1 -GenerationTarget 6 -ReportName live-people-generation.json
```

该命令真实消耗接口额度。报告逐次写入 `.tools`，明确区分已允许谈论、实际新增线索、模型原文、保守回退与未发送的前置拒绝。开发报告可包含已批准和被拒绝的虚构设定用于审核，不是玩家界面，也不包含鉴权头、API Key 或原始推理。测试存档不进入正式存档目录或交付包。

本轮发现并修复的实际问题包括：候客后合法的回访倾向变化误触发身份冻结、十二月星座数组越界、失败新建导致旧档目录提前清空、正式回访改期的来源校验、720p 新增按钮挤压正文，以及单看意图误以为线索已披露的测试指标问题。

真实服务的各轮结果、拒绝原因和有限人工检查结论会与本地规则检查分开记录；语义审核可能误拒或漏判，不能把通过有限测试说成对任意输出的绝对保证。

### 本轮真实结果

创建与对白均使用 PJLab 的 `deepseek-v4.1-flash`。V5 实际后台并发创建、独立审核并保存 **6 位主来客及各自关联人，用时 93.006 秒**，最大同时 HTTP 请求为 2；期间有 4 次草稿未获批准。此前也保留了等待 180 秒仍未满 6 位的失败记录，目标数量并非固定完成时间。已修复所有语义拒绝都等待 30 秒导致的补充过慢：结构或语义拒绝后短暂退避，网络与限流故障仍保持较长退避，二者不能互相覆盖。

随后检查发现，个别身份纠正会无来源地加上「我连远门都少出」或「我连这城南都还没转明白」。已同步加强生成提示、独立审核提示及 Godot/Python 本地规则，并验证有真实资料支持的地域经历仍可表达。关系内部往事的语义重叠也促使公开投影收紧为姓名与关系类型，原始已批准事实保持不变。

修复后 V7 使用**同六份原已批准包**在新隔离存档重放，逐项核对 generation ID、人物 ID、联系人、哈希、初始事实和审核来源完全一致。重放入档约 2.538 秒，**没有新增人物创建请求**，不能将这段耗时当作创建提速。实际对话覆盖两位主来客、其中一位正式跨日回访，以及一位关联人；另外四位没有逐个做真实对话，只完成六组共十二个案例的公开投影检查。

|V7 同包对白复测|结果|
|---|---|
|实际发网交谈|18 轮：17 条模型原文，1 次规则保护后本地回退|
|未获准的隐藏材料请求|另有 2 次在发网前拒绝，不计入等待均值|
|自动检查|43/43，通过接待、介绍、预约、实际离店、次日、读档及同人物新来访链路|
|全十二案例公开投影审计|128/128；内部关系历史和隐藏材料没有进入未获准的公开投影|
|18 轮玩家动作等待|平均 **3.807 秒**，中位 **3.162 秒**，范围 **2.122–9.909 秒**，包括一次回退|

等待从 `main.run_action` 开始到保存及两个无界面处理帧结束；当时同机有本地完整回归并行运行。最慢一轮的独立审核约 7.976 秒，不能将这些数字解释为纯模型生成速度或显示器点击延迟。回访提示确实带入此前实际谈话与已披露线索，但复测的回忆提问同时获准当前诉求话题，因此也不能夸作「无提示独立回忆」实验。

逐句人工检查未发现 V7 新的实质事实冲突或隐藏材料提前泄漏，两次身份纠正只确认了已有姓名和职业。开发记录为 `.tools/live-people-generation-final-v5.json`、`final-v6.json`、`final-v7.json` 及对应 V7 QA、十二案例公开投影报告；均不进入试玩包。四模型切换另发现的无来源固定习惯及其修复见[接口切换验证](api-model-switch.md)。最终本地回归、图形检查和导出记录见[整合验收](verification.md)。
